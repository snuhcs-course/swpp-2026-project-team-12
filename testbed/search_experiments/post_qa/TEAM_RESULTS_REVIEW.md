# 전달받은 Post QA 결과 검토

2026-11-05. 입력: `team/iter3/talkdock-family-week-100-eval.zip`.
분석 대상: `post_qa.json`, `queries.json`, 원문 manifest, 읽기 전용 SQLite, Neo4j JSON export.
유료 호출·DB 복원·공유 앱 변경 없음. 아래 정답 수는 전달받은 judge 판정이며 재채점한 성능이 아니다.

## 결론

기존 / 번갈아 선택 / reranker 세 조건은 유지한다. 그러나 선택 개선만으로 해결되지 않는 검색 누락, 시간 메타데이터 충돌, 답변 추론, 평가 오류를 따로 분류해야 한다.
현재 점수 38%를 곧바로 모두 모델 오류로 해석하지 않는다. 기존 결과와 분리한 평가 보정안을 먼저 확정하고 원래 점수도 함께 남긴다.

## 실제 수치

- 100케이스, judge correct 38/100, no_stale_or_invented 60/100.
- label 기준 raw recall 97.5%, budget 후 64%. 42/100케이스에서 budget 후 recall 감소.
- required label을 모두 확보한 54건 중 35건 정답, 19건 오답 판정.
- required label을 모두 확보하지 못한 46건 중 3건 정답, 43건 오답 판정.
- 이 교차표는 label 기준이다. 19건 모두를 '근거 충분한데 LLM이 실패'로 분류하면 안 된다.
- 원문 사진 파일은 100개, SHA-256으로 고유 사진 40장. 과거 평가에서 예상한 '100장 모두 다른 사진' 조건과 구분한다.

## 1. 후보 선택에서 중요한 변경 기록이 빠짐

| Probe | 질문의 핵심 | 실제 변경 기록 | 기존 정답 수 |
|---|---|---|---:|
| school | 현재 전시 장소 | 도서관 앞 로비 | 0/5 |
| tomato | 현재 화분 위치 | 창가 안쪽 | 0/5 |
| laundry | 니트 소유자 | 수진이 자기 것이라고 명시 | 0/5 |
| exercise | 변경된 산책 코스 | 시장 뒤 골목길 | 0/5 |
| album | 현재 스캔 담당 | 준호 | 0/5 |

다섯 probe 25건 모두 raw label recall 1, budget 후 0.
그래프 export에도 해당 변경 게시물 episode와 1024차원 임베딩은 존재하지만 그 episode를 근거로 한 RELATES_TO fact는 0개다. episode가 뒤에서 잘리는 설명과 일치한다.
따라서 번갈아 선택과 통합 재정렬 비교는 직접적으로 의미가 있다. 이것만으로 최종 정답 개선폭을 확정하지는 않는다.

## 2. 검색에 없는 근거와 잘못된 required/optional 구분

`basil-probe`: “왜 초록이라고 부르고, 누가 나눠준 화분이야?”
필수 label은 BASIL_ALIAS 하나이고 BASIL_GIVER는 optional이다. 원문의 정답은 선희가 모종을 나눠줬다는 내용이다.
다섯 케이스 모두 label recall은 1이지만, raw 검색 결과의 게시글 목록에도 `basil-gift`는 없다. 모두 이름만 답하고 제공자를 답하지 못해 0/5다.
검색어는 한 케이스에서 제공자 부분 자체가 빠졌고, 나머지 네 케이스는 제공자를 묻는데도 해당 게시글을 찾지 못했다. 질문 분리만 하면 다 해결되는 것도 아니다.

수정 제안:
- 평가 overlay에서 BASIL_GIVER도 필수 답변 요소로 명시. 원본 평가셋은 보존.
- 이름 붙인 이유를 실제로 설명한 기록은 `basil-core`. `basil-water`의 “초록이에 물을 줬다”는 이름의 유래를 직접 입증하지 않는다.
- 선택 실험의 기본 검색 후보는 유지하고, 이 케이스는 upstream retrieval failure로 보고. 검색어 보완은 후속 실험으로 분리.

## 3. 원문과 fact의 시간 해석 충돌

`dog-update` 원문(10/15): “이번 달부터 평일 저녁 콩이 산책은 지민이 맡기로 했어요.”
검색된 fact에는 valid_at 10/1, invalid_at 10/13이 들어 있다. 반면 10/13의 도윤 담당 fact는 invalid_at이 없다.
답변 모델에 지민 담당 원문이 들어온 케이스에서도 도윤을 현재 담당으로 답했다.
이것은 원문과 추출된 시간 메타데이터 사이의 충돌이다. 입력만으로 답변 모델의 내부 판단 원인을 확정할 수는 없지만, 순서만 바꿔 해결된다고 가정해서는 안 된다.

수정 제안: 이번 선택 비교에서는 그래프를 고치지 않고 이 케이스를 별도 집계한다. 후속 실험에서는 '현재 상태 질문에는 같은 대상·속성에 대한 명시적 변경 기록과 그 기록 시점을 대조하고, 추출된 invalid_at만으로 원문을 버리지 않는다'는 규칙을 따로 검증한다.

## 4. 필요한 내용이 있는데 답을 잘못 조합함

- `lunchbox-probe`: 수진이 도시락을 준비하기로 했다는 원문과 지민이 재료를 장바구니에 담았다는 원문이 함께 전달됐다. 답변은 준비 담당을 지민으로 바꿨다. 장보기 행동과 준비 담당을 혼동한 사례다.
- `cafe-probe`: 카페 하루라는 명칭이 fact와 원문에 있는데도 일부 답변은 이름을 확인할 수 없다고 했다. 전체 판정 2/5.
- `laundry-core`의 “선희가 세탁망에 넣었다”는 행위는 선희 소유라는 근거가 아니다. 검색 누락과 별개로 '돌봄/세탁/운반한 사람 = 소유자' 연결을 막아야 한다.

수정 제안: 선택 A/B/C에서는 답변 프롬프트를 고정한다. 대표 실패에 최소 정답 근거를 직접 제공하는 진단 조건을 소수 추가하면 검색 선택 실패와 답변 실패를 구분할 수 있다. 이 조건은 정답 정보가 들어가는 oracle 진단으로 별도 표시한다.

## 기존 코드 유지 여부

- `baseline`, `interleave`, `reranker` 선택 알고리즘은 이번 검토로 바꾸지 않았다.
- 선택 전 후보 고정, 답변 프롬프트 고정, 동일 5개 budget도 유지한다.
- 자동 감사 스크립트 `audit_team_export.py`를 추가했다. `outputs/team_export_audit.json`에서 probe별 판정과 graph 출처를 확인할 수 있다.
- 다음 실행기 보완: 원래 label recall 외에 질문별 필수 답변 요소 확보율을 overlay로 별도 계산하고, 위 오류 유형을 결과에 표시한다. overlay는 검수 확정 후 적용한다.

## 제공된 파일과 실제 실행 준비 상태

받은 것: SQLite, media·사진, manifest, ID 매핑, pipeline 상태, 평가 결과·judge cache, Neo4j graph export.
그래프는 81 episode(80 post + registry), 102 fact, 총 105 node / 281 edge다.
기존 답변에서 선택된 고유 memory 75개는 모두 export에서 찾았고, 저장된 source 원문과 graph content의 불일치는 0개다. 기존 그래프를 재사용할 근거가 충분하므로 construction부터 다시 할 필요는 없다.

없는 것: budget 전 전체 memory 배열, 실제 최종 Responses 요청, 실행 commit·최종 적용 설정을 명시한 별도 기록.
`queries.json`은 게시글별 순위 분석이지 전체 fact/episode 후보 덤프가 아니다. `post_qa.json`도 budget 적용 후 memories만 있다.

따라서 이전 요청의 완전한 replay는 지금 자료만으로 불가능하다. 하지만 실험 자체는 다음 방법으로 진행 가능하다:
1. export를 기존 서비스와 분리된 Neo4j에 복원. 이 과정은 API 호출 없이 가능하며 제공된 restore 스크립트는 실행 전 검토한다.
2. 저장된 검색어로 검색만 다시 실행해 raw 후보를 고정. embedding 호출 비용만 발생할 수 있다. 원래 실행의 후보와 완전히 같다고 주장하지 않는다.
3. 실제 본문·사진·질문자·관계·고정 시각으로 공통 입력을 재구성한다. 캡처 없는 과거 요청을 만든 것처럼 표시하지 않는다.
4. A/B/C를 모두 새 baseline과 함께 비교한다. 이전 38%는 참고치로만 둔다.
5. 먼저 전체 100케이스에서 선택 지표를 확인하고, 예비 답변 20 probe × 1 viewer × 3방식 = 60건으로 호출·채점·지연 기록을 점검한다. 문제가 없으면 100케이스 × 3방식 × 3회로 확장한다.

이번 턴에는 1~5의 실제 실행은 하지 않았다. 유료 실험 승인 전 검수 항목과 입력 시점을 확정해야 한다.
